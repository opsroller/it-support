# NixOS administration

A NixOS system is a function of its configuration. Administering it
means changing that configuration, building it, and switching to it,
with the previous system always one command away.

## Where configuration lives

- **Flake** (preferred): `flake.nix` with `nixosConfigurations.<host>`,
  inputs pinned in `flake.lock`, kept in git. `nixos-rebuild` reads it
  with `--flake .#<host>`.
- **Classic**: `/etc/nixos/configuration.nix` and channels. Treat it the
  same way: under version control, changed by edit and rebuild.
- Split by concern into modules (`hardware.nix`, `gpu.nix`,
  `virtualisation.nix`, `users.nix`); `hardware-configuration.nix` is
  generated by `nixos-generate-config` and only regenerated, not
  hand-tuned.

Find the host's configuration from the project profile; if it is not
in version control, that is the first finding.

## Software: which layer

| Need | Where |
|---|---|
| A service, driver, desktop feature, or anything with a module | The module's options (`services.*`, `programs.*`, `hardware.*`, `virtualisation.*`) |
| A tool every user of the machine needs | `environment.systemPackages` |
| A tool one user wants | Home Manager `home.packages` / `programs.*`, or `users.users.<name>.packages` |
| Tools one project needs (compilers, SDKs, linters) | That project's `flake.nix` `devShells`, entered with `direnv` and an `.envrc` of `use flake` (nix-direnv caches it) |
| A one-off run | `nix run nixpkgs#<pkg>` or `nix shell nixpkgs#<pkg>`; nothing persists |

Search for the package or option first (`nixpkgs-search`). Never
`nix-env -i` or `nix profile install` on a managed machine.

## Changing the system

1. Edit the module; keep the change small and in the module for its
   concern.
2. `nixos-rebuild build --flake .#<host>` (or `nix build
   .#nixosConfigurations.<host>.config.system.build.toplevel`):
   evaluation and build errors surface here, nothing is activated.
3. Compare: `nix store diff-closures /run/current-system ./result`
   shows exactly which packages change version or appear.
4. `nixos-rebuild test --flake .#<host>`: activate now, but keep the
   boot entry on the old system, so a reboot undoes it. Use
   `dry-activate` to list the units that would restart.
5. Verify the change does what was asked.
6. `nixos-rebuild switch --flake .#<host>`: activate and make it the
   boot default. Use `boot` instead for kernel, driver or initrd
   changes that need a reboot anyway.
7. Commit the configuration change with a Conventional Commit; the
   commit and the running generation must match.

Remote hosts: `nixos-rebuild switch --flake .#<host> --target-host
<user>@<host> --use-remote-sudo` builds locally and copies the closure.

## Rolling back

- `nixos-rebuild switch --rollback`, or pick the previous generation in
  the boot menu.
- `nixos-rebuild list-generations` (or `nix-env --list-generations -p
  /nix/var/nix/profiles/system`) lists them with dates.
- A rollback is a stopgap: fix the configuration and rebuild forward,
  or revert the commit, so the next `switch` does not bring the fault
  back.

## Unfree, insecure and broken

- Unfree (NVIDIA, CUDA, some firmware): `nixpkgs.config.allowUnfree =
  true`, or narrower `nixpkgs.config.allowUnfreePredicate` naming the
  packages. Firmware: `hardware.enableRedistributableFirmware`.
- Insecure: `nixpkgs.config.permittedInsecurePackages` with the exact
  name and version, a comment saying why, and a date to remove it.
- Broken: do not force `allowBroken`; pick another version or report.

## Inputs, pins and upgrades

- `nix flake update` moves every input; `nix flake update <input>`
  moves one. Commit `flake.lock` with the reason.
- Upgrade between releases by changing the nixpkgs input to the new
  release branch, reading its release notes for removed or renamed
  options, building, `test`, then `switch`. Keep `system.stateVersion`
  at the release the machine was installed with unless the release
  notes say how to migrate.
- A package from another nixpkgs revision: a second input
  (`nixpkgs-unstable`) and `inputs.nixpkgs-unstable.legacyPackages.${system}.<pkg>`
  or an overlay naming only that package. Never move the whole system
  to get one package.
- Overrides: `pkg.override { ... }` for build options (for example
  `cudaSupport = true`), `overrideAttrs` for source or patches; record
  why next to it.

## Caches and builds

- `nix.settings.substituters` and `trusted-public-keys` for extra
  binary caches (the CUDA cache, a team cache); rebuild once before the
  new cache is used.
- `nix.settings.max-jobs` and `cores` to keep big builds from starving
  the machine; remote builders through `nix.buildMachines`.
- `nix.settings.experimental-features = [ "nix-command" "flakes" ]`
  where flakes are used.

## Store and generations

- `nix.gc.automatic`, `nix.gc.dates` and `nix.gc.options = "--delete-older-than 30d"`,
  and `nix.optimise.automatic`; keep enough generations to roll back
  past the last risky change.
- `boot.loader.systemd-boot.configurationLimit` (or GRUB's) keeps
  `/boot` from filling.
- `nix path-info -Sh /run/current-system` and `nix-store --gc
  --print-roots` explain what holds space.

## Secrets

Never put a secret in a Nix expression: everything evaluated lands in
the world-readable store. Use a secrets module that decrypts at
activation (sops-nix, agenix) or a file outside the store read by the
service at runtime (`*File` options such as `passwordFile`).

## Output

A committed configuration change, built, tested and switched (or
left at `test` with the reason), with the generation number, the
closure diff, and how to roll back.
